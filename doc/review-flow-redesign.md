# 口コミ投稿フロー仕様

更新日: 2026-09-23

本書は現在の5ステップ口コミ投稿、公開表示、集計、開発用投稿者の仕様を示す。再設計は実装済みであり、現在のコードとの差分は[実装状況](./implementation-status.md)を優先する。

## 1. 方針と対象範囲

手入力を減らして職場の雰囲気・働きやすさを回答しやすくする。正確な勤務年や自由入力の表示名を収集せず、公開プレビューで掲載内容を確認できるようにする。

変更対象は投稿画面、入力検証、DB・保存処理、公開口コミ表示、店舗評価の集計、ダミーデータ、開発用投稿者の運用・リセット、テストと関連文書。認証実装、ベクトル検索、タグによる店舗検索は対象外。

旧形式のダミー口コミは開発用コマンドで確認してから削除し、新仕様のseedへ移行する。公開取得処理は新仕様の必須項目が揃った口コミだけを返す。

ベクトル検索は実装・維持コストに対するメリットを踏まえて見送る。新フローに外部AI API呼び出しを含めない。

## 2. 全5ステップの共通仕様

1画面1ステップとし、進捗・戻る・次へを表示する。戻っても入力を保持する。自由記述はStep 4だけ。各画面の検証に加え、最終送信時にサーバーで全項目を検証する。送信中の二重操作を防ぎ、失敗時は入力を維持する。

既存の配色（#FF6A2B、#75402A、#FFCAB3）を使用し、スマートフォンのタップ領域、キーボード操作、フォーカス、選択状態の読み上げに配慮する。

## 3. Step 1: 属性入力

以下はすべて必須の単一選択。

| 項目 | 選択肢 |
| --- | --- |
| 在籍状況 | 現在勤務中／退職から1年未満／退職から1年以上 |
| 働いていたときの立場 | 高校生／大学生・専門／フリーター／主婦・主夫／その他 |
| 勤務期間 | 3ヶ月未満／3ヶ月以上〜1年未満／1年以上 |

「立場」は雇用契約の区分ではなく投稿者属性。勤務中は投稿時点、退職者は勤務当時の属性を回答する。勤務期間は勤務中なら投稿時点まで、退職者なら勤務した期間。ちょうど3ヶ月は中央の区分、ちょうど1年は「1年以上」に含める。

テストユーザー選択、勤務開始年・終了年、表示名・ニックネームの自由入力を廃止する。公開バッジは属性からサーバー側で自動生成する。例: 「現役スタッフ / 大学生・専門」「退職したスタッフ / フリーター」。在籍状況には「投稿時点」と添え、時間経過で回答を自動更新しない。

## 4. Step 2: 定性タグ

| 設問 | 選択肢 | 制約 |
| --- | --- | --- |
| 職場の雰囲気に近いものは？ | 和気あいあい／静か・もくもく／業務中は集中／元気・活発 | 必須、1〜2つ |
| 一緒に働いていたスタッフはどんな層が中心でしたか？ | 学生が多め／主婦・主夫層が多め／フリーター・Wワーク中心／高校生〜シニアまで幅広い | 必須、1〜2つ |
| 店長の関与度 | ほぼ常駐している／シフトによって半々／ほぼ不在・現場任せ | 必須、単一選択 |

雰囲気タグの案内は「近いものを1〜2つ選んでください」。スタッフ層の案内は「1〜2つ選択」。雰囲気・スタッフ層のどちらにも組み合わせによる排他制御を設けない。選択中のチップは再タップで解除でき、上限到達時にも解除可能とする。

サーバーでも選択肢の許可リスト、件数、重複、型を検証する。雰囲気タグとスタッフ層は、どちらも1〜2つを必須とする。

## 5. Step 3: 定量評価

以下の4項目は必須。未選択から開始し、1〜5のrange入力をスライダーとして表示する。キーボードの矢印、Home、End等でも操作でき、現在値と両端の意味を表示する。5をポジティブに揃える。

| 項目 | 1の説明 | 5の説明 |
| --- | --- | --- |
| 職場の雰囲気 | ギスギス | アットホーム・風通し良 |
| 教育・フォロー体制 | 放置気味 | 手厚いフォロー |
| 業務のゆとり（体力・精神的負荷） | 息つく暇なし | 落ち着いて作業できる |
| シフトの融通度 | 変更が難しい | 予定に柔軟 |

おすすめ度は「ぜひ勧めたい／人・条件による／あまり勧めない」の必須単一選択。総合点には含めない。総合評価の直接入力を廃止する。

## 6. Step 4: 生の声

- 設問: 「この職場で働いて感じたことを教えてください」
- 補足: 「職場の雰囲気、人間関係、忙しさ、研修・サポート、シフトの入りやすさなど、実際に働いて分かったことを自由に書いてください。」
- 「職場の雰囲気」「人間関係」「忙しさ」「シフト」「研修・サポート」を書き方のヒントとして常時表示する。
- 必須、30〜300文字。
- プレースホルダー: 「例：働いて感じたことを自由に入力してください」
- 入力中も参照できる記入例をテキストエリアの下へ常時表示する。

旧形式の3つの必須記述と別枠の総合コメントをこの1項目に置き換える。文章の重複保存・重複表示はしない。前後の空白を除いた文字数をUnicodeコードポイント単位で表示・検証し、クライアントとサーバーの数え方を揃える。禁止語を検出し、本文をHTMLとして解釈しない。

## 7. Step 5: 公開プレビューと同意

実際の公開口コミカードと共通の表示部品で、属性バッジ、投稿時点の在籍状況、勤務期間、タグ、各評価・総合点、おすすめ度、短文を確認する。

氏名や正確な日時は公開しない。口コミが5件未満の店舗では日付を「○年○月」、5件以上では「○年○月上旬・中旬・下旬」とする。プレビューでは予定表示であることを区別する。属性や本文から身元が推測される可能性は残るため、「特定されない」と断言しない。

「誹謗中傷・個人攻撃・実名記載を行っていないこと」のチェックを必須にし、ガイドラインへのリンクと版を示す。サーバーは同意が明示的にtrueであることと、確認した版が現在の版であることを検証する。古い版なら再確認を促す。保存する版・同意日時はサーバーで確定し、口コミと同じトランザクションで保存する。

このチェックは投稿内容に関する同意であり、自動審査や実名検出を保証しない。利用規約への同意も求める場合は対象文書・同意文を整合させる。

## 8. 評価集計

1. 口コミの総合点は4つの必須評価の算術平均。
2. 店舗の評価軸別・総合点は、公開対象の口コミを勤続期間と在籍状況で重み付けした平均。
3. 勤続期間の重みは3ヶ月未満0.8、3ヶ月以上〜1年未満1.0、1年以上1.1。在籍状況の重みは勤務中1.2、退職1年未満1.0、退職1年以上0.7。口コミごとの重みは両者の積。
4. 店舗集計値は小数第1位へ丸めて `stores` に保存する。
5. 評価順は全体平均3.2、事前重み3.0のベイズ補正値を使用する。画面表示と最低評価の絞り込みは補正前の重み付き総合点を使う。
6. おすすめ度は総合点に含めない。

例: 4・4・3・4の口コミ総合点は3.75で、口コミカードでは3.8と表示する。店舗集計では4軸それぞれと3.75へ口コミの重みを掛ける。非公開・非表示・削除済み、勤務期間または4評価が欠けた口コミを除外し、対象0件は0点ではなく「—」とする。

一覧と詳細の表示、最低評価の絞り込みは `overall_score`、評価順は `bayesian_score` を使用する。口コミカードとプレビューの総合点は各口コミの4評価から計算する。いずれもブラウザが送った総合点を採用せず、サーバーまたは共有Schemaの関数で計算する。

## 9. 開発用投稿者の運用（確定）

1. 1ユーザー・1店舗の制約を維持する。DBの一意制約で同時投稿も防ぐ。
2. ダミー口コミの投稿者と手動確認用の固定テストユーザーを別IDにする。seedは固定ユーザーの口コミを作らない。
3. 固定テストユーザーの投稿だけをリセットする開発用コマンドを用意する。
4. 固定ユーザーは明示的に有効にした開発環境だけで使用する。通常の公開環境では認証未導入の間は投稿を受け付けない。

投稿者IDはサーバー内部で決定し、フォーム入力として受け付けない。将来は投稿者取得処理をログイン中のユーザーID取得に差し替える。認証・セッションは今回実装しない。

実装は `NODE_ENV=development`、`ENABLE_DEV_REVIEW_POSTING=true`、localhostへのDB接続、`DEV_DATABASE_NAME`との一致、DB名に`dev`・`test`・`local`のいずれかを含むことをすべて必須とする。条件を満たさない場合は直接POSTでも保存前に拒否し、UIでも投稿不可を案内する。公開環境でフラグだけ有効にしても投稿できない。

重複時に既存投稿を自動上書きしない。共有DBでは全開発者が固定ユーザーの投稿枠を共有することを明記する。

## 10. 開発用リセット

`pnpm run db:reset-test-reviews` として実装済み。

- 開発環境と明示フラグを確認し、意図した開発DBであることを検証できる構成にする。NODE_ENVだけで削除可否を決めない。
- 対象ユーザーは内部で固定し、任意のユーザーIDを引数で受け付けない。
- 固定ユーザーの口コミと紐づく回答・評価・タグ・同意記録だけを削除する。ダミー投稿者の口コミ、店舗、ユーザー本体、フォーム定義は残す。
- 引数なしでは対象件数を表示するだけの確認モードとする。`-- --execute` を明示した場合だけトランザクションで削除し、0件でも正常終了する。
- 接続文字列・本文・秘密情報をログに出さず、削除件数を報告する。
- 共有DBでは他の開発者にもリセットの影響が及ぶことを文書化する。

## 11. DB・公開応答・ダミーデータ

`reviews` に在籍状況、立場、勤務期間、雰囲気タグ、スタッフ層タグ、店長の関与度、おすすめ度、ガイドライン版・同意日時、生の声を保存する。正確な勤務年と自由入力の表示名は新投稿で収集しない。`review_ratings` に1〜5の評価を保存し、型・範囲・外部キー・一意制約を設ける。`review_reactions` は口コミ、固定テストユーザー、許可されたリアクション種別の組み合わせを主キーにする。

フォーム・評価軸定義、入力検証、保存処理を一緒に更新する。口コミと関連情報を同一トランザクションで保存し、失敗時に部分データを残さない。詳細な内部エラーを公開しない。

公開応答は必要な表示項目だけに限定する。内部ユーザーID、正確な投稿日時、同意日時を公開レスポンスやHTMLのdateTimeに含めない。内部処理では正確な日時を保持できるが、公開日付はサーバーで日本時間の年月、または上旬・中旬・下旬へ変換する。

50店舗に、内容の異なるダミー口コミを計32件用意し、5件未満の粗い属性表示と5件以上の詳細表示、新仕様のタグ・点数・おすすめ度のバリエーションを確認できるようにする。固定テストユーザーの投稿枠は空ける。

既存マイグレーション履歴を不用意に書き換えず、クリーンDBと既存開発DBの適用・再生成手順を定義する。ベクトル検索を試したDBには追加テーブルや適用履歴が残る可能性がある。ブランチを切り替えてもDB状態は戻らないため、実装時に対象DBを確認して手順を選ぶ。

## 13. 受け入れ条件

- 全5ステップを完了でき、戻っても入力を保持する。手入力はStep 4だけ。
- 必須項目の検証がUIとサーバーで一致する。
- 雰囲気タグは0件・3件を拒否し、1〜2件のすべての組み合わせを受け入れる。
- 未知の選択肢、重複タグ、不正な型、評価の0・6・小数を直接送信しても拒否する。
- 短文の空白除去後29・30・300・301文字、空白のみ、改行、絵文字を検証する。
- スクリプト風・SQL風の入力でコード実行やSQL注入が起きず、HTMLとして描画しない。
- 同意なし、文字列のtrue、古いガイドライン版を拒否し、日時・保存版の改ざんを採用しない。
- userIdや総合点の改ざんで投稿者・計算結果を変更できない。
- 開発フラグ未設定・無効、公開環境で直接POSTを拒否する。
- 同一ユーザー・店舗への同時投稿は1件のみ成功し、他方は重複となる。
- リセットで固定ユーザーの投稿と関連情報だけが消え、ダミー口コミや店舗が残る。途中失敗のロールバック、0件・再実行を確認する。
- 4・4・3・4の口コミ総合点は3.75となり、おすすめ度で変わらない。店舗集計は勤続期間と在籍状況の重みを反映し、評価順は少数口コミを全体平均へ補正する。非公開・削除済みを除外し、0件は未評価になる。
- 公開応答・HTML・プレビューに内部ユーザーIDや正確な日時が混入しない。
- スマートフォン幅・キーボードで入力、選択解除、エラー、投稿操作を確認する。
- Lint、型チェック、単体テスト、Build、DB適用・seed、主要ブラウザ操作を確認する。

## 14. 実装状況と変更時の注意

開発用投稿の境界、マイグレーション・seed、検証・保存、5ステップUI、公開表示・集計、リアクション、限定リセットは実装済み。DB・環境変数・投稿制御を含む変更は詳細レビュー対象とし、認証実装とは分けて扱う。

表示桁数、Unicodeコードポイントによる文字カウント、環境変数、コマンド名は本書とコードを同時に更新する。DB変更前には必ず接続先を確認し、確認モードを経ずに削除コマンドを実行しない。
